# Несколько пользователей (multi-user)

Шлюз из коробки обслуживает много пользователей, у каждого — свой Claude-аккаунт и свои cookies.

## Как это устроено

```
Клиент A ──basic_auth(alice)──> Caddy ──X-Remote-User: alice──> Gateway ──cookies/alice.json──> claude.ai (как alice)
Клиент B ──basic_auth(bob)────> Caddy ──X-Remote-User: bob────> Gateway ──cookies/bob.json────> claude.ai (как bob)
```

- **Caddy** проверяет basic_auth и передаёт имя пользователя в заголовке `X-Remote-User`
- **Gateway** по имени пользователя подгружает его cookie-файл `cookies/<user>.json` и подставляет в запросы к claude.ai
- Ассеты (`/p/assets-*`) проксируются без cookies и без basic_auth (это публичные JS/CSS)

## Добавить пользователя

На сервере, из каталога проекта:

```sh
./add-user.sh alice            # пароль сгенерируется (или: ./add-user.sh alice 'пароль-12+')
```

Скрипт:
- генерирует bcrypt-хэш и добавляет пользователя в `Caddyfile`
- создаёт cookie-слот `gateway/cookies/alice.json`
- перезапускает Caddy

## Первый вход пользователя (self-service)

Пользователю **не нужен** удалённый браузер. Он логинится сам через шлюз:

1. Устанавливает расширение, вводит в Options свой host + user + pass
2. Открывает `https://claude.ai`
3. Видит страницу логина Claude (cookies пока нет — шлюз проксирует без них)
4. Вводит email → получает magic-link → кликает
5. Claude выставляет session-cookies → **шлюз перехватывает их** в `cookies/<user>.json`
6. Дальше пользователь работает авторизованным

Cookies при этом остаются на сервере и не попадают в браузер клиента.

## Изоляция и безопасность

- Имя пользователя санитизируется (`a-zA-Z0-9._-`) — защита от path traversal
- `X-Remote-User` выставляет только Caddy после basic_auth; gateway удаляет клиентский `x-remote-user` и не доступен публично (только внутри docker-сети)
- Gateway удаляет `Authorization` перед форвардингом в claude.ai
- Значения cookies не логируются

## Расчёт ёмкости: сколько пользователей выдержит один сервер

Gateway — это прокси без видео-кодирования, поэтому очень лёгкий. Узкое место — **полоса** и (при большом числе одновременных) CPU на TLS/проксирование.

### Расход на одного пользователя

| Ресурс | Активный пользователь | Примечание |
|---|---|---|
| RAM (gateway) | ~5-15 MB | один процесс Node на всех, per-user — только cookie-файл в памяти |
| CPU | ~0.01-0.05 vCPU | проксирование + переписывание HTML/CSS |
| Полоса | ~0.5-2 Mbps | API/SSE-стриминг + ассеты (ассеты кэшируются Cloudflare) |
| Диск | ~10-50 KB | cookie-файл |

Ключевое отличие от видео-стриминга: **нет кодирования видео**, поэтому на пользователя уходит в ~50 раз меньше CPU и RAM.

### Ёмкость по конфигурациям сервера

Считаем по **одновременно активным** пользователям (стримят ответы Claude прямо сейчас). Зарегистрированных может быть в разы больше (cookies лежат на диске, не едят ресурсы, пока пользователь не активен).

| Сервер | RAM | vCPU | Одновременно активных | Зарегистрированных* | Полоса-лимит |
|---|---|---|---|---|---|
| 1 vCPU / 1GB | 1GB | 1 | ~15-25 | ~200+ | ~10-20 активных (полоса) |
| 1 vCPU / 2GB | 2GB | 1 | ~25-40 | ~500+ | ~20-30 активных |
| 2 vCPU / 4GB | 4GB | 2 | ~60-100 | ~2000+ | ~50-80 активных |
| 4 vCPU / 8GB | 8GB | 4 | ~150-250 | ~5000+ | ~150-200 активных |

\* Зарегистрированных ограничивает только диск (по ~10-50KB на cookie-файл) — практически не лимит.

### Главный лимит — полоса, не CPU/RAM

Каждый активный пользователь тянет ~0.5-2 Mbps (текстовый стриминг Claude). Считаем по полосе сервера:

| Исходящая полоса сервера | Одновременно активных |
|---|---|
| 100 Mbps | ~50-150 |
| 500 Mbps | ~250-750 |
| 1 Gbps | ~500-1500 |

### Пример под конкретную ВМ

Для дроплета **2 vCPU / 4GB / 4TB transfer** (~$24/мес):

- CPU: 2 vCPU / 0.05 = ~40 активных по CPU
- RAM: 4GB — gateway ~256MB на всех, не лимит
- Полоса: 4TB/мес ≈ ~12 Mbps средний sustained → ~6-12 активных непрерывно стримящих
- **Итого: комфортно ~30-50 одновременно активных, ~500-1000 зарегистрированных**

Для **4 vCPU / 8GB** (~$48/мес): ~100-150 активных, несколько тысяч зарегистрированных.

### Как увеличить ёмкость

| Приём | Эффект |
|---|---|
| Cloudflare перед сервером, кэширование ассетов | ассеты (основной объём) отдаются с edge CF, не с сервера → −70% полосы |
| `cache-control: public` для JS/CSS (уже включено) | ассеты кэшируются, не перекачиваются |
| Несколько серверов + round-robin DNS | линейное масштабирование |
| Сжатие ответов (gzip/br) | −трафик на тексте |

### Практическое правило

**~0.05 vCPU + ~1 Mbps на активного пользователя.** RAM почти не лимит (один gateway на всех). Планируйте по полосе и числу одновременно активных, а не по числу зарегистрированных.
